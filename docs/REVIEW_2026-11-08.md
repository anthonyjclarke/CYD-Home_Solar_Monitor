Reviewed `1.0.1` on `main` at `9805d26`, comparing it with the previous audited commit `cdcb226`. Inventoried 141 tracked files and inspected the 61 changed paths, with particular attention to the new transport, provisioning, dashboard and build-budget code. Existing README badge edits were present before review and were left untouched.

The repository has materially improved. The earlier Improv memory faults are fixed and now have sanitizer coverage; optional tiles and live polling have transition tests; portal and source-age fixes are present; compressed assets have restored usable flash headroom. No recurrence of the earlier `P1` parser issue was found in the checks run here.

The highest-priority follow-up is still transport resilience. Accepted body bytes are bounded, but an open silent connection can block acquisition indefinitely, and the new buffer does not recover from its own allocation failure. A separate history-refresh race can briefly display data belonging to the previous configuration. These are the three findings below; they remain open after this documentation review.

## Open findings

All three are `P2`: maintenance corrections with concrete failure conditions. IDs `R1`–`R3` distinguish this review from the previous `F1`–`F8` register.

### R1 – P2: Sink deadlines do not stop a silent HTTP body

Locations: `src/data/ha_source.cpp:35`, `:122` and `:195` in the [reader](../src/data/ha_source.cpp). The relevant pinned dependency is Arduino-ESP32 `2.0.17`, `HTTPClient::writeToStreamDataBlock()` at dependency lines 1381–1455.

The 5-second HA and 10-second weather deadline is evaluated only from `LimitedBody::write()`. The pinned HTTP client loops while connected and waiting for body bytes; when `available()` returns zero it only yields. That loop does not consult the sink, enforce an elapsed deadline, or inspect source cancellation. `setTimeout()` does not bound this availability-wait path. The same gap applies after a partial body, not just before its first byte.

Reproduced using the actual extracted client body loop and production `LimitedBody`, with a simulated connected peer reporting no bytes. A 5,000 ms sink budget never fired; the operation returned only when the simulated remote closed at 20,000 ms. Keeping that peer connected leaves the loop running. This is a host control-flow reproduction, not a new real-board network test.

Impact: the one reader task cannot complete its cycle, publish subsequent readings, switch configuration or fetch the other source. Values eventually become stale, but acquisition cannot recover until the connection closes or the device restarts. If the stalled connection is HTTPS HA, the current TLS watchdog pause also remains active for that session. The earlier documentation already qualified the sink-only deadline; marking F4 fully closed still overstates transport coverage.

Correction: enforce idle and total deadlines in a layer that runs during availability waits, including chunk metadata waits, and can close the owned connection on timeout or cancellation. Preserve HTTP/1.1 framing, chunk decoding and connection reuse after complete valid responses. Do not replace the byte cap with another full-body read.

Acceptance: drive the actual transport path with headers followed by silence, a partial fixed-length body, a partial chunk, stalled chunk metadata, slow progress and configuration/pause cancellation. Assert elapsed bounds and a succeeding later request. Add the test permanently; `tests/test_body_limit.cpp` alone cannot detect this failure.

### R2 – P2: The bounded buffer can terminate on allocation failure

Location: `include/body_limit.h:16` in [BodyLimit](../include/body_limit.h), called by `LimitedBody::write()` before the reader checks the transport return value.

`BodyLimit::accept()` calls `std::string::append()` and then reports the whole block accepted. Standard string allocation failure throws; there is no failure-to-short-write conversion. The application is compiled with `-fno-exceptions`, and there is no recovery handler around the append. The code therefore cannot promise that all buffer allocation failures become normal HTTP read errors.

Reproduced on the host by injecting failure into the first heap allocation needed by an otherwise valid 100-byte append. `std::bad_alloc` propagated out of `accept()` rather than returning zero. Inspection of the fresh target ELF also found `std::__throw_bad_alloc()` calling `__cxa_throw`; this review did not induce an actual board reset. Treat termination/reset as the target risk, not as a newly observed hardware event.

The size check limits stored payload, but string capacity growth and allocator overhead can consume more than the logical byte count. The current body tests assert content size and refusal of oversize blocks; they do not inject allocation failure or measure peak capacity. Low heap is already a demonstrated project constraint from the recorded weather TLS investigation.

Correction: use storage with explicit allocation-failure reporting, such as a carefully sized nothrow buffer or bounded incremental storage whose allocator failure becomes a sticky short write. Budget peak memory, not just final payload size. Re-enabling exceptions globally solely to handle this append would require separate flash/runtime assessment.

Acceptance: fail each growth/allocation step, verify that the read is rejected without terminating or publishing partial state, then verify a later request can succeed. Keep both oversize-body and allocation-failure coverage.

### R3 – P2: A forced history refresh is lost while an old request is running

Locations: `src/web/web_page.h:262`–`:264`, and the settings submit handler at `:345`, in the [dashboard](../src/web/web_page.h).

The settings save requests `refreshHistory(true)`, but the first guard returns whenever `historyBusy` is true, including forced calls. An outstanding history response from before a URL/entity/location change can then arrive, replace the chart with old-configuration data and set `historyFetched` to the current time. Ordinary refreshes refuse another fetch for a minute. The live-status sequence guard does not cover history.

Reproduced by extracting the production history refresh function: start an old deferred request, invoke a forced refresh while busy, resolve the old response, then invoke a normal refresh. Only the old fetch ran; its data was rendered and the next fetch was suppressed by the 60-second cache. The live-status race tests do not exercise this separate history path.

Correction: invalidate a history generation when settings affecting identity are saved; discard replies from an older generation and queue a forced refresh if one is already running. Do not leave an old chart looking like the newly selected source. Prefer retaining a clear loading/unavailable state while obtaining the new history.

Acceptance: save a new mapping/location during a pending old history fetch, return responses in both orders, and confirm that old data is never accepted after invalidation and that the required fresh request runs. Include failed-save behaviour so an unsuccessful save does not unnecessarily discard valid history.

## Guidance for the next changes

### Prioritize resilience and acceptance

Fix R1 and R2 together with transport-level failure injection, then R3 with deferred history requests. These improve failure behaviour without adding network load or changing the data model. Avoid a framework migration to solve these narrow issues. Add small permanent harnesses for the worker's weather gate and Wi-Fi lifecycle when those areas next change; static branch inspection is weaker than the new parser/dashboard regression coverage.

The recorded board observations now provide useful evidence for live readings, HTTP weather, minimum heap and history restoration. They remain short observations from specific builds, not a soak or comprehensive update test. Highest-value physical acceptance remains both update mechanisms/app slots, interrupted or invalid uploads, Improv provisioning after bounds hardening, power cuts during checkpoints, sustained TLS HA operation and night/touch behaviour across midnight/DST. No hardware checklist box was ticked during this review.

### Keep transport and update policy explicit

Plain HTTP weather is a deliberate documented response to measured heap failure. It exposes coordinates and permits unauthenticated weather replies; do not silently restore HTTPS or claim verified weather transport. If revisiting it, measure the largest free heap block and peak handshake demand alongside the frame buffer, history and HTTPS HA. A trusted local weather relay is a separate optional design, not a required feature or a claim that direct HTTPS now fits.

`source::pause(true)` is still a request to stop future work, not confirmation of an idle reader. Cancellation is checked after an entity request; totals and the weather branch can still run before the next outer-loop check. If updating OTA orchestration, introduce explicit ownership/quiescence across HTTP upload and ArduinoOTA rather than adding another independent flag. No concurrent-update corruption was reproduced here; this remains a design/acceptance item.

The inbound settings limit remains post-read, and HTTP mutation headers remain a cross-site browser guard rather than LAN authentication. Preserve the existing trust description. For direct firmware upload, consider progress and an inactivity timeout appropriate to uploads rather than reusing the 15-second small-request limit; a lost completion response also needs an outcome that distinguishes an uncertain update from a verified failure.

### Use the recovered flash margin deliberately

The unmodified reviewed source rebuilt from a fresh directory at 1,646,928 actual image bytes, leaving 188,080 bytes in a 1,835,008-byte OTA slot. That is about 184 KiB free and 122,544 bytes above the 64 KiB policy floor. Linker-reported app use was 1,640,357 bytes (89.4%); static RAM remained 74,800 / 327,680 bytes (22.8%). These static figures do not establish runtime heap health. Build metadata and documentation changes can alter exact counts.

The screenshot/footer compression and automated actual-image budget address the previous flash concern. Keep partitions unchanged and retain the image-generation budget check. Before a large UI feature, account for the margin needed by maintenance and extra embedded help rather than spending the entire recovered space.

Useful next enhancements are a redacted diagnostic export, visible reader progress/last-success time and a device history storage-health view using state already available. They would make R1-like stalls and checkpoint failures easier to diagnose. Source-specific heartbeat grouping remains an option if mappings span independent integrations; preserve the idle-battery behaviour while testing that change. Energy/cost views should use proper HA energy entities rather than integrating the sparse five-minute snapshots.

### Keep documentation and telemetry provenance accurate

The previous review was retired during documentation consolidation. Its fixes are traceable through commits and the changelog, but a short current register should retain partially resolved work such as F4. Use this review for R1–R3 until closed with evidence; avoid restating all eight earlier issues as still open.

The committed history fixture contains real power, SOC, energy/weather values and timestamps with timezone metadata. Its inspected schema contains no HA token, URL, entity mapping, IP address or coordinates. It is still owner telemetry, not synthetic or anonymous test data. Keep the documented existing exception separate from permission to collect more captures. The preview server and handbook mostly explain this distinction already; the generic synthetic-only sentence in the hardware guide has been corrected.

Corrected the handbook's remaining obsolete weather statement: HTTP weather needs Wi-Fi and one completed HA cycle when a token is set; it does not need a synchronized clock or a successful source read. Corrected the obsolete claim that the centre layout hides unknown age: F8 now has explicit warning text. Also clarified that the browser's 12-second limit applies to each status request, not exactly 12 seconds since the panel last answered. The timer interval can add delay before the next request starts. Historical changelog assertions were retained, with this follow-up linked from a new `Unreleased` entry.
